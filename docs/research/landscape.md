# Jourilo — Landscape Research

Accessed: 2026-10-30

Scope: tools adjacent to Jourilo, a developer-first, local-first CLI and Claude Code plugin that drives a real browser (Playwright) to audit UX, accessibility (WCAG 2.2 AA), performance (Core Web Vitals) and conversion friction, traces issues to source, and verifies fixes.

Conventions:
- Every factual claim links to the source it came from. Version numbers come from the npm registry (`registry.npmjs.org/<pkg>`, queried 2026-10-30) unless stated otherwise.
- **unverified** = we could not confirm the claim from a primary source during this pass.
- "Opportunity for Jourilo" rows are our own analysis, not facts about the other tools.
- Pricing changes often. Treat every pricing row as a snapshot from the access date.

## 2. Browser automation

### 2.1 Playwright

|                   |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What it does      | Automates Chromium, Firefox and WebKit, headless or headed, on Windows, macOS and Linux. Has bindings for Node.js (TS/JS), Python, Java and .NET. Ships Playwright Test, a runner with assertions, isolation, parallelism, sharding, retries, an HTML reporter and UI Mode ([intro](https://playwright.dev/docs/intro)).                                                                                                                                                                                                                                                                                                                                                                    |
| Strengths         | Auto-waiting, web-first (retrying) assertions, an isolated browser context per test, codegen, Trace Viewer (DOM snapshots, network, console, screenshots), and role/label/test-id locators ([playwright.dev](https://playwright.dev/)). ARIA snapshots give a YAML view of the accessibility tree for `toMatchAriaSnapshot()` ([aria-snapshots](https://playwright.dev/docs/aria-snapshots)). The docs describe agent tooling: an MCP server, a CLI for coding agents, and accessibility-tree snapshots ([playwright.dev](https://playwright.dev/)). The docs recommend `@axe-core/playwright` for a11y scans ([accessibility-testing](https://playwright.dev/docs/accessibility-testing)). |
| Limitations       | Raw CDP access (`newCDPSession`) is "only supported on Chromium-based browsers" ([BrowserContext](https://playwright.dev/docs/api/class-browsercontext)). Lighthouse user flows are documented only with Puppeteer ([user-flows](https://github.com/GoogleChrome/lighthouse/blob/main/docs/user-flows.md)), so running Lighthouse inside Playwright needs integration work. A working Playwright-plus-Lighthouse recipe is **unverified**. The Playwright docs themselves say automated a11y tests "cannot detect all types of WCAG violations" ([accessibility-testing](https://playwright.dev/docs/accessibility-testing)).                                                               |
| License / pricing | Apache-2.0, free ([npm](https://registry.npmjs.org/playwright)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Opportunity       | Its trace, locator and a11y-tree primitives are the raw material for evidence-carrying findings. Jourilo adds the layer on top: journeys, audit rules, mapping findings to source, and re-verifying fixes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

### 2.3 Selenium and WebDriver BiDi

|                   |                                                                                                                                                                                                                                                                                                                                                             |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What it does      | Selenium is a W3C-WebDriver-based automation suite. WebDriver BiDi adds a WebSocket channel so the browser can stream events (network, console, JS errors) to the client. Selenium calls BiDi "the cross-browser replacement for the Chrome DevTools Protocol" ([Selenium BiDi](https://www.selenium.dev/documentation/webdriver/bidi/)).                   |
| Strengths         | Standards-based, multi-vendor. Bindings for Java, Python, C#, Ruby, JavaScript and Kotlin ([Selenium BiDi](https://www.selenium.dev/documentation/webdriver/bidi/)).                                                                                                                                                                                        |
| Limitations       | WebDriver BiDi is still a **W3C Working Draft** (dated 8 October 2026) ([W3C TR](https://www.w3.org/TR/webdriver-bidi/)). Selenium says its low-level BiDi domains are reachable but undocumented, and that CDP support "is temporary until WebDriver BiDi has been implemented" ([Selenium BiDi](https://www.selenium.dev/documentation/webdriver/bidi/)). |
| License / pricing | Apache-2.0 ([npm selenium-webdriver](https://registry.npmjs.org/selenium-webdriver)).                                                                                                                                                                                                                                                                       |
| Opportunity       | Long-term interoperability. Jourilo should isolate CDP-only features (e.g., trace capture) behind an adapter so it can move to BiDi as the spec matures.                                                                                                                                                                                                    |

### 2.4 Why Playwright for Jourilo

These are justification points, each tied to a source. They are not claims that Playwright is better than the alternatives.

1. **Three engine families, one API.** Chromium, Firefox and WebKit ([intro](https://playwright.dev/docs/intro)). Puppeteer lists Chrome and Firefox only ([pptr.dev](https://pptr.dev/)). WebKit coverage matters for Safari-relevant UX checks.
2. **Evidence capture built in.** Trace Viewer records DOM snapshots, network, console and screenshots ([playwright.dev](https://playwright.dev/)), which fits Jourilo's "every finding has evidence" goal.
3. **Accessibility-tree primitives.** ARIA snapshots ([aria-snapshots](https://playwright.dev/docs/aria-snapshots)) plus the documented axe integration ([accessibility-testing](https://playwright.dev/docs/accessibility-testing)).
4. **Agent ecosystem fit.** Playwright ships an MCP server and agent CLI ([playwright.dev](https://playwright.dev/)), which matches the Claude Code plugin surface.
5. **Known costs we accept:** CDP is Chromium-only ([BrowserContext](https://playwright.dev/docs/api/class-browsercontext)), and Lighthouse flows are Puppeteer-first ([user-flows](https://github.com/GoogleChrome/lighthouse/blob/main/docs/user-flows.md)). Performance tracing will therefore be Chromium-centric.

## 3. Lab auditing

### 3.1 Lighthouse (including user flows)

|                   |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What it does      | Automated lab audits. The README's CLI help lists the categories `accessibility, best-practices, performance, seo`, and it requires Node 22 LTS or later ([repo](https://github.com/GoogleChrome/lighthouse)). The v13.3.0 notes add a "New agentic browsing category" to the default config. Its contents and scoring are **unverified** ([v13.3.0](https://github.com/GoogleChrome/lighthouse/releases/tag/v13.3.0)).                                                                                              |
| User flows        | Three modes ([user-flows](https://github.com/GoogleChrome/lighthouse/blob/main/docs/user-flows.md)). **Navigation**: one page load, full performance score. **Timespan**: an arbitrary period with interactions; no overall perf score, no LCP, no a11y category. **Snapshot**: the current DOM state, good for a11y deep in SPAs; no perf metrics. Multi-step flows require the Node API with Puppeteer (`startFlow`).                                                                                              |
| Strengths         | Industry-standard lab report. Accessibility audits are weighted "based on axe user impact assessments" and link to axe rule docs ([a11y scoring](https://developer.chrome.com/docs/lighthouse/accessibility/scoring)).                                                                                                                                                                                                                                                                                               |
| Limitations       | The a11y score covers only automated pass/fail audits. Manual audits (focus traps, tab order, landmarks) don't affect the score ([a11y scoring](https://developer.chrome.com/docs/lighthouse/accessibility/scoring)). Lab data can't measure INP directly ([lab vs field](https://web.dev/articles/lab-and-field-data-differences)).                                                                                                                                                                                 |
| Recent changes    | Lighthouse 13 (Oct 2025) removed many legacy perf audits from the report and JSON in favor of shared "insights" (e.g., `layout-shifts` became `cls-culprits-insight`). It requires Node 22.19+ ([Lighthouse 13 blog](https://developer.chrome.com/blog/lighthouse-13-0)). The PWA category was removed in v12 ([v12.0.0](https://github.com/googlechrome/lighthouse/releases/tag/v12.0.0)). v13.6.0 (2026-10-27) changed default report filenames ([releases](https://github.com/GoogleChrome/lighthouse/releases)). |
| License / pricing | Apache-2.0 ([npm](https://registry.npmjs.org/lighthouse)).                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Opportunity       | Lighthouse audit IDs change across majors. Jourilo should pin a version and map audit IDs to its own stable finding IDs. Timespan mode cannot report LCP, so Jourilo needs both navigation runs and journey-level measurement.                                                                                                                                                                                                                                                                                       |

### 3.2 axe-core

|                      |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What it does         | Accessibility rules engine covering WCAG 2.0/2.1/2.2 at A, AA and AAA, plus best practices ([repo](https://github.com/dequelabs/axe-core)). `axe.run` returns `violations`, `passes`, `incomplete` and `inapplicable` ([API.md](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Documented limits    | The README says axe finds "on average 57% of WCAG issues automatically" ([repo](https://github.com/dequelabs/axe-core)). Deque's study puts it at 57.38% (169,242 of 294,958 issues across 13,000+ pages/states) ([Deque](https://www.deque.com/automated-accessibility-testing-coverage/)). That figure counts **issue volume, not success criteria**. Deque says the common 20–30% figure counts criteria instead. Items needing manual verification were not counted. The report's publication date is **unverified**.                                                                                                                                                                                                                                                                                                                                                                                        |
| "Incomplete" results | Results "aborted and require further testing": either a technical limit or a JS error. Interfaces can surface them for manual review ([API.md](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md)). Many rules, including `color-contrast`, can return "needs review" ([rule-descriptions](https://github.com/dequelabs/axe-core/blob/develop/doc/rule-descriptions.md)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| WCAG 2.2 caveat      | The only `wcag22aa` rule is `target-size` (SC 2.5.8), and it is **disabled by default** "until WCAG 2.2 is more widely adopted and required" ([rule-descriptions](https://github.com/dequelabs/axe-core/blob/develop/doc/rule-descriptions.md)). `color-contrast-enhanced` (AAA) and `experimental` rules are also off by default ([API.md](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md)). Whether `runOnly: { type: 'tag', values: ['wcag22aa'] }` alone enables `target-size` is **unverified**. Enable it explicitly with `rules: { 'target-size': { enabled: true } }`.                                                                                                                                                                                                                                                                                                                    |
| 4.11–4.14 changes    | No release labeled breaking ([CHANGELOG](https://raw.githubusercontent.com/dequelabs/axe-core/develop/CHANGELOG.md), [releases](https://github.com/dequelabs/axe-core/releases)). **4.14.0 (2026-10-05):** enables `label-content-name-mismatch` by default and adds new violations to some existing rules, so issue counts may rise. It also claims 20–40% faster runs. **4.13.0 (2026-08-05):** ElementInternals support on by default; `aria-allowed-attr` flags deprecated ARIA attributes as needs-review; deprecates `commons/matches/fromPrimative`. **4.12.0 (2026-06-01):** new `aria-tab-name` rule; deprecates `landmark-complementary-is-top-level`; new APIs including `axe.resetLocale()`, exposed `normalizeRunOptions`, and `enabled` in `getRules()`. **4.11.0 (2025-10-07):** adds `RGAAv4` tags, and some best-practice rules now carry both tags, so filters on `best-practice` must update. |
| License / pricing    | MPL-2.0 ([npm](https://registry.npmjs.org/axe-core)). `@axe-core/playwright` 4.14.0 is also MPL-2.0 ([npm](https://registry.npmjs.org/@axe-core/playwright)). Deque sells commercial products, which are not evaluated here.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Opportunity          | Treat `incomplete` as a first-class "needs human review" queue, not as noise. Pin the axe version and fingerprint findings, since result counts change between minors. Pair the scans with manual checks of the criteria axe cannot cover (see standards.md).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

## 7. Positioning for Jourilo

### Jourilo should be

1. **A local-first developer loop.** Run on a laptop or in CI against localhost or a preview URL. Produce evidence (traces, screenshots, a11y-tree snapshots, axe output) and point to the likely source location.
2. **An orchestrator of established engines, not a replacement for them.** Use Playwright for driving, axe-core for rules, and Lighthouse/DevTools-style metrics for lab performance. Pin versions and cite the engine and rule ID in every finding.
3. **Honest about coverage.** Label every result as _automated-confirmed_, _needs human review_ (e.g., axe `incomplete`), or _manual check required_. Label every performance number as **lab**. Never present lab INP as a Core Web Vitals pass or fail ([web.dev](https://web.dev/articles/lab-and-field-data-differences)).
4. **A fix verifier.** Re-run the same journey and rules after a change, and report fixed, still failing or regressed.
5. **Complementary to field tools.** Accept hints from analytics/replay exports and hand hypotheses to experimentation platforms.
6. **Privacy-preserving by default.** It runs on the developer's machine against their own app and collects no end-user data.

### Jourilo should NOT be

1. **A field RUM or session-replay product.** Clarity, Contentsquare, PostHog, Amplitude and FullStory already cover production observation.
2. **An experimentation platform.** No traffic splitting, no flag serving, no production stats engine. Leave that to GrowthBook, Optimizely, Wingify, PostHog and Amplitude.
3. **A WCAG conformance certifier.** Automated tools cover only part of WCAG (57% of issues by volume per Deque, and fewer criteria). A "WCAG 2.2 AA compliant" badge would be misleading.
4. **A Core Web Vitals verdict.** Google assesses CWV at the 75th percentile of real page loads ([web.dev/vitals](https://web.dev/articles/vitals)), and a local lab run cannot produce that.
5. **A new rules engine competing with axe-core,** or a new automation library competing with Playwright.
6. **A source of superiority claims.** Describe what Jourilo does and its limits. Do not rank it against the tools above.
